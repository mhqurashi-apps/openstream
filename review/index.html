OpenStream

UI/UX review · draft 1 · 16 Nov 2026

The client app and the server application are two halves of one product, so they get one system. This review covers what ships today, the corrections the audit found, and a redesigned server that lives in the system tray instead of a window you have to find.

01

What ships today

Screenshots are the running app on a physical Android device, captured during the release acceptance run. Every defect below was read in the source, not guessed from the picture.

Hierarchy
The dashboard is an AppBar labelled "OpenStream Client" over a plain list. The app bar names the project rather than the user's task, and nothing on the screen says which computer is the one you want.
Repeated action
Every computer card carries a filled "Connect" button with identical weight, so a screen with three computers presents three equal claims. The one you used last looks the same as the two that have been offline for a week.
Duplicated call
"Pair Computer" appears twice in the empty state, as a floating button and again as the empty-state action. Pairing always opens a bottom sheet, which on a tablet leaves a wide window with a sheet pinned to the bottom edge.
One shape for all
The status badge and the connection pill are both fully rounded, and the floating button is a stadium. Nothing in the interface has a distinct shape, so nothing has a distinct role.
Theme leaks
The session screen holds thirteen hardcoded colours, nine raw hex values and four Colors.* constants. In light mode a white surface card floats over black video, and the "Disconnected" pill is maroon in both themes.
Collision
In the session screen the "Waiting for your computer…" placeholder sits behind the error card and the two overlap. The faint placeholder text is still readable through the card.
Wrong default
The session screen defaults its host size to 1920 by 1080. On any host that is not exactly 1080p, pointer and keyboard coordinates land in the wrong place. The real display size has to be reported by the host.
No tablet layout
The list is clamped to 760 logical pixels and centred. On a tablet that is a narrow column in a wide window, not a layout.

What changed and why

One primary action per state. The computer you used last gets the filled button, the others get a quiet one. The screen now has a focal point instead of three equal claims.

Pairing once. The empty state offers pairing in the body. The header link is the only other entry point, so the call is never made twice on one screen.

Words instead of pills. "LAN Direct" reads as a status without a capsule, and the dot gives the eye something to land on when scanning a list.

A paired computer can be forgotten. The phone keeps the key in its own keychain, so it has to be able to drop it. Today the delete call exists in the keychain but no screen reaches it.

Session specifics

Chrome off the video. The status bar and the control bar sit on solid surfaces above and below the picture, so a white window on the remote desktop can never wash them out.

Rotated for portrait. A 16:10 desktop in a portrait phone wastes half the screen. Rotating the picture 90° fills it, and the host reports its true display size so coordinates still land correctly.

One error, one place. The failed state replaces the picture entirely. The placeholder and the error can no longer be on screen together.

The server tray

The server is a background service, so its interface should live in the background too. One tray icon carries the state. Clicking it opens a panel that answers three questions: is this machine sharing, who is watching right now, and how do I let someone in.

Why a tray and not a window

The daemon has no window to lose. It already runs as a background service with a metrics endpoint and a CLI onboarding path. A window would add a thing to find and close.

The icon carries the state. A filled glyph means sharing. The panel opens only when the user asks for it, and the state is legible from the icon alone.

One panel, three questions. Sharing state, who is watching, and how to admit someone. Everything else, permissions and curtain, is one row each and stays out of the way.

Why validity is configurable

A code that never expires is a permanent key. On a shared or borrowed machine the pairing code outlives the reason it was created. An expiry makes the window explicit.

Single use covers the common case. Pairing a phone and then finding the code on a sticker in a meeting room is a real failure. Single use closes it.

Until revoked is the honest default for a personal desktop, with a visible countdown so the user knows when it changes.

Why the connection view is thin

It shows what the host already measures. Frame counts, encoder, resolution and input counters come from the metrics the daemon keeps today.

The peer name is marked as a proposal. The protocol hello carries no device name yet, so the panel shows the fingerprint and labels the name field as something to add.

Disconnect is on the host. The daemon owns the session, so the host can end it without asking the phone.

Why this is a panel and not a tray row

Revocation is rare and deliberate. A user who wants to cut a device off should not have to hunt for it, but it should not sit in the way of the common case either. So the tray carries a count, and this panel opens from it.

Every row states what it breaks. Revoking a device is not a soft action. The dialog says the device has to pair again, because that is the actual consequence.

Revoke all is separated from the rest. It is the only action that touches everything, so it sits alone at the bottom with its own label.

Why codes are listed next to devices

They are different things that look alike. A trusted device is a key in the store. An issued code is a secret that has not been used yet. Both grant access, so both belong in one place.

An expired code is kept for the record. It shows that the code existed and that it was spent, which is the difference between "expired" and "never issued".

Revoking a code stops it being read. It cannot be redeemed later, so a code seen in a photo has a shelf life the user controls.

This panel cannot be built on the daemon as it stands. The trust store holds a Vec<[u8; 32]> of public keys and offers pair(). It has no remove, no revoke and no expiry, so a paired key stays trusted for the life of the file. The store also keeps no label and no timestamp, so a device cannot be shown by name or by when it was paired. Both the store format and the daemon need to change before this panel can show a true row.

06

What the server needs to add

The panel above is a design. Four things it shows do not exist in the daemon yet. Each one is a small, contained change, and the code already has the shape to hold them.

Token expiry
The trust store holds a flat list of Ed25519 public keys with no expiry and no use count. Expiring a pairing code means storing an expiry alongside each key and rejecting a key that has passed it. The store is one file with one JSON document, so this is contained.
Single use
The enrollment secret is currently reusable. Single use means marking the secret as consumed on first successful pairing, which the enrollment path can do at the point the new key is written to the store.
Peer identity
The client hello carries the screen size, the codecs and the key, but no device name. Adding a short label to the hello gives the tray a name to show instead of a fingerprint. The hello is signed, so the field is authenticated once added.
Disconnect
The daemon owns the peer connection and the pipeline, so ending a session from the host is local work. The tray button should be the only path, so the phone cannot hold a stream open against the owner's intent.
Revoke
The trust store holds a list of public keys and offers a pair method. There is no remove, no revoke and no expiry, so a key that is written stays trusted for as long as the file exists. Revocation needs a remove on the store, a rewrite of the file, and a route to reach it from the tray.
Device records
The store keeps a bare key and nothing else. There is no name, no paired-at time and no last-seen time, so a list of trusted devices could only ever show a fingerprint. Each record needs those three fields, which means a second version of the store file.
More than one viewer
The daemon publishes each new session into a single slot, so the most recent client replaces the previous one rather than joining it. A panel listing everyone connected is only honest once the host can hold several sessions at once.
There is already a seam for this. The daemon defines an OnboardingGui trait with exactly the calls a tray needs: show the pairing QR, show the current permission step, reflect the privacy curtain, open a settings URI, and signal that the host is ready. The tray app is an implementation of that trait and nothing more. The headless recording implementation already used by the tests proves the model works without a GUI toolkit.
The two findings that matter most. First, the trust store cannot revoke: it pairs a key and never forgets one. Second, the daemon holds a single session slot, so a second client replaces the first rather than joining it. Both are read from the source, not inferred from the design.
What is real in this mockup. The QR code was produced by the OpenStream pairing library from a synthetic host key, and the six words "actress pelican hand disorder raven fortune" are the checksummed encoding of that same synthetic fingerprint under the shipped word algorithm. The screen copy is the shipped copy. The metric field names are the real field names from the metrics endpoint. The connected-peer name, the expiry control and the single-use control are proposals, and the panel labels them as such.
